# HireLens AI — Evaluation Package

This is the evaluation package for HireLens AI, built for the Match Hire /
Moss "5-Day Remote AI OS Sprint" deliverables: 8-12 test cases with expected
behavior, a baseline comparison, pass/fail results, failure analysis, and
quality/speed/cost/human-intervention metrics.

**Ground rule this whole package follows:** nothing here is fabricated. No
evaluation result is recorded unless it was actually produced by running
`run_evaluation.py`, no timing/accuracy/cost number is invented, and no
real Groq API call is made without first showing what will run and roughly
how many requests it will make.

## Contents

| File | What it is |
|---|---|
| [`test_cases.json`](./test_cases.json) | The 12 evaluation cases: scenario, input, condition tested, expected behavior, pass/fail criteria. Machine-loadable by the runner; human-readable on its own. |
| [`rubric.md`](./rubric.md) | The explicit evaluation rubric (evidence grounding, requirement classification, score behavior, error handling, output completeness, human decision boundary) with pass/fail criteria and a rubric-to-test-case matrix. |
| [`run_evaluation.py`](./run_evaluation.py) | The reproducible evaluation runner. Executes cases against the real pipeline code, records real pass/fail + timing, writes `results.json` / `results.md`. |
| [`harness.py`](./harness.py) | Shared fixtures used by the runner: scripted fake LLM services, poison-pill fakes, forbidden-phrase rubric check, canonical job descriptions. Test scaffolding only — never a reimplementation of pipeline logic. |
| [`test_data/`](./test_data/) | Synthetic candidate CVs (`.docx`) and invalid-input fixtures, generated by `test_data/generate_test_data.py`. All names/employers are fictional. |
| [`baseline.md`](./baseline.md) | Honest description of the manual-review workflow HireLens replaces, and what has vs. hasn't actually been measured against it. |
| [`failure_analysis.md`](./failure_analysis.md) | Four documented failure scenarios: the real Gemini→Groq quota migration, plus three reproduced failure modes (ambiguous evidence, malformed LLM output, invalid documents). |
| [`results.md`](./results.md) / [`results.json`](./results.json) | Actual, measured results from the most recent run(s). Generated — do not hand-edit. |
| [`proxy_user_feedback.md`](./proxy_user_feedback.md) | Informal proxy-user usability evaluation (not recruiter/HR validation) — output comprehension, contrast-test scores, and a UX improvement suggestion. |

## How the 12 cases are organized

Every case has one of three **modes**, so cost/quota concerns are explicit
and controllable:

- **`deterministic`** — pure application code, no LLM constructed at all.
  Free, instant, always safe to run.
- **`mocked`** — the real pipeline/service classes, wired to a scripted fake
  LLM service (fixed, canned responses) or a fake that deliberately raises a
  provider-style error. No network call. Free, safe to run.
- **`live`** — the real `HireLensPipeline` wired to the real
  `GroqLLMService`. Makes real Groq API calls and costs quota. Only runs
  with explicit opt-in (see below).

| ID | Scenario | Mode |
|---|---|---|
| TC-01 | Strong alignment candidate | live |
| TC-02 | Moderate alignment candidate | live |
| TC-03 | Low documented alignment candidate | live |
| TC-04 | Missing required skill evidence | deterministic |
| TC-05 | Ambiguous / partial evidence | mocked |
| TC-06 | Preferred qualifications missing | deterministic |
| TC-07 | Sparse / minimal CV | mocked |
| TC-08 | Invalid or unsupported document input | deterministic |
| TC-09 | LLM / API service failure | mocked |
| TC-10 | Input variation (formatting / wording) | live |
| TC-11 | Empty input validation | deterministic |
| TC-12 | Full dossier structural completeness & decision-boundary check | mocked |

Full detail for every case (candidate input, JD input, expected behavior,
pass/fail criteria, assertions) is in `test_cases.json`.

## Running the evaluation

From the repository root, with the project's virtual environment active
(`GROQ_API_KEY` only needed for `live` mode):

```bash
# List every case, its mode, and what it tests. No execution.
python evaluation/run_evaluation.py --list

# Run every free case (deterministic + mocked) -- the default, no API cost.
python evaluation/run_evaluation.py

# Run only one category explicitly.
python evaluation/run_evaluation.py --mode deterministic
python evaluation/run_evaluation.py --mode mocked

# Run a single case by ID.
python evaluation/run_evaluation.py --case TC-06

# Live mode is gated: without --yes, this only prints the plan (which
# cases, and an estimated API-call count per case) and exits -- it makes
# NO real API calls.
python evaluation/run_evaluation.py --mode live

# Actually execute the live cases (real Groq API calls, costs quota):
python evaluation/run_evaluation.py --mode live --yes

# Run absolutely everything, including live:
python evaluation/run_evaluation.py --mode all --yes
```

Each run updates `results.json` (merging into any prior results by test ID,
so you can run `deterministic` and `mocked` today and `live` later without
losing earlier results) and regenerates `results.md` from it.

To regenerate the synthetic CV fixtures under `test_data/` (e.g. after
editing `generate_test_data.py`):

```bash
python evaluation/test_data/generate_test_data.py
```

## Reading the results

`results.md` has two sections:

1. **Executed results** — a table of every case that has actually been run:
   scenario, mode, expected behavior, the *actual* observed result, PASS /
   FAIL / ERROR, and measured execution time. Nothing in this table is
   estimated.
2. **Prepared but not yet executed** — every case not yet run in this
   environment (typically the four `live` cases, until run with
   `--mode live --yes`), so it's always clear what has and hasn't actually
   been verified.

## Relationship to the existing test suite

This package is intentionally separate from `tests/` (pytest,
`pytest.ini`-scoped, 157 unit/integration tests against fakes/mocks — see
the main [README](../README.md#testing)). `tests/` verifies the
implementation is correct at the unit/integration level on every commit;
this evaluation package verifies end-to-end *product behavior* against the
scenarios a recruiter would actually encounter, including scenarios (a real
live LLM call, a simulated provider outage) that `tests/` deliberately never
exercises. Both should pass; neither replaces the other.
